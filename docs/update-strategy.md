# 更新、完整备份与恢复

更新日期：2026-10-22。beta.19 增加 GitHub 在线检查、自动下载与自建镜像接入口，保留完整私有备份、恢复工具和受签名离线更新。beta.18 及之前版本不会凭空获得这些按钮，需先离线升级一次。按平台逐步操作、文件选择与故障处理见 **[各平台更新教程](update-guide.md)**。Windows 独立环境曾完成离线升级与失败恢复演练；Linux、macOS、Docker 及在线更新的真实发布升级结果以本版 Release 和[开发日志](development-log.md)为准，不能用打包或 CI 通过代替完整升级验收。

## 1. 用户只需做什么

更新包为.ccupdate，原签名密钥和数据格式保留。旧.wlupdate/.wlbackup继续支持。beta.4及更早程序仍需下文所述手动过渡；beta.18及更早版本需先用原离线入口更新一次，才能使用新的联网入口。

正常更新前保存编辑器草稿，并等到“所有更改已保存”。通过安装根的 `start.cmd`（Windows）、`start.sh`（Linux/macOS）或Windows桌面窗口运行，主管理员在后台操作：

1. 点击“检查更新”，查看版本、说明和当前系统是否有兼容更新包。
2. 有兼容新版时点击“下载并安全更新”，随后自动下载、验证，并进入原有备份和安装流程。

仍可使用离线入口：点击“选择更新包”，选择官方 `.ccupdate`，验证通过后点击“备份并更新至 …”。网络不可用时不影响继续创作或导入已下载的包。

下载期间尚未暂停创作，备份以实际安装前排空写入后的资料为准。若下载完成时当前页面有未保存内容、页面不可见或已离开后台，不会自动重启；保存后在后台继续更新。刷新或重新进入后台也不会自动执行旧下载任务。仅下载阶段可取消，进入验签阶段后不能再取消，以避免准备状态竞争；安装任务提交后更不能中断备份或切换。程序不会在无人点击时后台安装，也不自动刷新编辑页面。

程序自动准备运行组件、暂停写入、创建完整备份、验证恢复、切换版本和核对全部资料。成功后使用原账号登录；其他仍打开的旧页面若有草稿，应先复制或保留内容再刷新，旧页面写入会被拒绝，不能要求它先保存到新版。程序不自动刷新正在编辑的页面。失败会显示真实状态；恢复未完成时保留现场并要求修复，不能伪装成功或引导重新初始化。

普通用户和次级管理员不能更新、下载完整私有备份或恢复安装。后台的“创作 JSON”只用于创作内容交换；“创建并验证完整备份”才包含账号、权限和图片。

默认下载源为本项目GitHub Releases，不需要填写GitHub令牌。公开测试版默认查看预发行频道，可切换到稳定版频道；稳定版频道不包含alpha/beta/rc。后台轮询的是本机任务进度，不会每隔几秒访问GitHub。检查结果会缓存，接口限流或网络失败显示错误，不影响创作。只有相同系统、CPU架构的受签名更新包才显示可安装，不能把普通ZIP/TAR下载包用于更新。

beta.19 发行按 Windows x64、Linux x64/arm64、macOS x64/arm64 分别提供标准名 `.ccupdate`，实际可用附件以对应 Release 为准。它们不能跨系统或架构使用，签名/归档校验通过也不等于所有平台都完成了原生升级与失败恢复演练。后台在线更新处理工作台后端；Windows 桌面“帮助 → 检查桌面程序更新…”独立处理 EXE、Electron 与随包运行组件，使用单独的官方签名桌面描述和全文件校验。现有 workspace 后端与固定运行时文件不被模板覆盖，后台和窗口版本分别核验。Docker 需使用宿主机流程。首次准备依赖和更新时的依赖准备仍需要 npm 网络或预先配置好的依赖源；程序包下载镜像不加速 npm 依赖下载。尚无定时备份、无人值守自动安装或下载断点续传。

### GitHub与国内镜像

在“更新来源与渠道”中可选择 GitHub 直连或自建 HTTPS 镜像。目前**没有已启用的国内加速服务**，也不内置来源不明的公共代理。镜像由发布者或安装维护者统一管理，普通用户不必各自搭站；可放在对象存储和 CDN，域名、备案、计费与访问质量需自行确认。相关产品要求见[阿里云 OSS 与 CDN](https://www.alibabacloud.com/help/en/oss/user-guide/cdn-acceleration)和[腾讯云 COS 源站加速](https://intl.cloud.tencent.com/zh/document/product/228/32977)。

填写镜像根地址，例如 `https://downloads.example.com/chronicle-cartarium`，不要带凭据、查询参数或片段。只支持公开HTTPS地址，内网和回环地址会被拒绝。镜像布局：

频道和镜像偏好保存在安装根 `.worldloom/online-update-settings.json`，不包含密码，不改变数据库连接或实际数据目录。完整资料恢复不搬运此下载偏好，未配置时回到 GitHub 默认源；这不影响世界、地图、图片和账号的恢复。

```text
chronicle-cartarium/
  releases.json
  v0.2.0-beta.19/
    chronicle-cartarium-0.2.0-beta.19-win-x64.ccupdate
```

以上为目录布局示例，不表示已经部署该镜像。`releases.json`采用GitHub Releases列表的数组结构；附件记录仍保留官方GitHub下载地址作为来源身份，实际镜像下载使用根地址加版本目录和包名。镜像检查或下载失败时回退到GitHub。镜像只能转发同一份官方包，不能提供替代公钥。下载验证大小与SHA-256之后，还必须通过程序内置公钥的Ed25519签名、平台、版本和数据格式检查；镜像清单中的摘要本身不是发布者身份证明。被控制的镜像仍可能隐藏新版或使检查失败，不能因此承诺即时可用性。

发布者可保存[官方Releases API列表](https://docs.github.com/en/rest/releases/releases)到本地JSON，准备对应原始更新包，再生成待上传目录：

```sh
node scripts/create-update-mirror.mjs --catalog public-releases.json --packages signed-packages --output new-mirror-directory
```

源包目录按附件名平铺；工具只复制清单中大小、摘要均匹配的`.ccupdate`，以及成对存在的 Windows 桌面 ZIP 和 `.update.json` 签名描述，净化发行字段，拒绝重复包和已有输出目录。最后才写`releases.json`，复制失败的目录不能上传。此工具不联网、不上传、不签名，也不会复制源目录中的其他文件；必须由维护者将生成目录发布到自己的HTTPS静态存储。始终先上传完整包、最后更新清单，避免客户端看到尚未就绪的版本。GitHub公开API存在[访问频率限制](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)，不应通过高频自动检查绕过。

## 2. 数据保护范围与兼容边界

| 项目         | 当前保护机制                                                                                                                                  |
| ------------ | --------------------------------------------------------------------------------------------------------------------------------------------- |
| 固定数据路径 | 启动器第一次将实际绝对 DATA_DIR 写入安装根 `.worldloom/current.json`，以后换程序不换此路径。新程序位于 `.worldloom/releases/`。               |
| 完整备份     | 数据库、全部普通上传文件和作者索引、安装设置、账户及授权、创作快照、显式指定的私有 `.env` 和散列清单。历史备份、更新缓存、进程锁不递归打包。  |
| 一致性       | 同一个维护门禁覆盖创作、上传、账号、权限与设置；先排空已接受的写入，再取得快照。单实例进程锁阻止同一个 DATA_DIR 被另一个服务打开。            |
| 恢复验证     | SQLite完整性检查并读取工作区；MySQL恢复到测试自身创建的全新库，比较领域内容后只删除此验证库；图片、私有文件和revision逐项校验。               |
| 更新来源     | 清单使用固定公钥验证Ed25519签名，校验每个文件、平台、架构、起点与格式；不是仅比较SHA-256。拒绝越界路径、链接、重复路径和超容量压缩包。        |
| 在线传输     | 仅HTTPS，逐跳验证公开地址并绑定已验证DNS结果；限制重定向、时间与流字节数，下载到全新临时文件。镜像回退仍执行相同大小、SHA-256及发布签名验证。 |
| 失败恢复     | 新版开放写入前失败时，恢复到全新目录/全新项目库，再启动原程序；原目录、原项目库、备份和失败现场保留。                                         |
| 新版已确认   | 完成记录在开放写入前持久化。一旦完成，即使开放保存请求的回应丢失，也不恢复升级前快照；正常重启/重试开放保存即可。                             |
| 浏览器旧页面 | 带旧版本号或缺少版本号的浏览器写入被拒绝；保留草稿并提示刷新。API脚本无Origin时可不带此头，仍受登录和权限检查。                               |

本版更新包仅支持**同一系统和架构**，且数据格式必须全部一致：MySQL schema 5、SQLite user_version 1、创作格式1、安装格式1、用户目录格式1。跨格式迁移尚未开放自动更新；先拒绝执行，等待对应版本经过迁移演练后实现。程序版本与数据版本分别管理，不靠版本号相近推断兼容。

SQLite在执行DDL前读取user_version，MySQL在DDL前读取现有迁移版本；更高未知版本拒绝启动，不把版本号降回当前值。安装和用户私有格式也在打开业务数据库前校验。已有本地库但缺少安装配置时拒绝重新安装。旧beta程序没有这些完整门禁，不能拿旧程序直接打开不兼容的新数据。

SQLite备份使用Node内置在线backup API，包含已提交WAL内容，再将**副本**整理为独立文件；不直接复制运行中的主库文件。[Node 22.18 SQLite backup](https://nodejs.org/download/release/v22.18.0/docs/api/sqlite.html#sqlitebackupsource-db-path-options)。仍为单Node进程服务，不支持另一个程序同时直接改库或上传目录；外部直接写入不在应用维护门禁内。

MySQL完整备份限定本项目标准schema 5和InnoDB表，保留行数据、建表结构、utf8mb4字符集及实际排序规则；额外表、视图、触发器、例程、事件及结构不一致会拒绝更新。验证/自动恢复要求账号有创建新项目库和删除其自身验证库的权限。只有本轮新建的验证库会删除；原库与失败的恢复库不删除。恢复始终先确认新库名不存在，再执行 `CREATE DATABASE`（没有 `IF NOT EXISTS`）。当前连接格式未单独验收含特殊TLS参数的MySQL部署。

## 3. 完整备份与迁机

主管理员点击“创建并验证完整备份”，成功后列表标为已验证。备份保存在实际数据目录 `backups/full-…`。需要带走时点“下载私有备份”，再次输入当前主管理员密码；下载的 `.ccbackup` 包包含账号密码哈希和数据库私有连接配置。

私有备份**目前不加密**，必须存放在私人或加密磁盘，不能发到公开仓库、公开网盘或静态网站。重认证是因为包包含整套安装凭据。程序不自动清理历史完整备份；请检查磁盘空间。保存在同一硬盘不等于异机备份，可定期下载到另一台机器/私有存储。

迁机使用与备份格式匹配的程序，在服务停止状态执行：

```sh
node --import tsx scripts/recover.ts /private/full-backup.ccbackup /private/new-chronicle-cartarium-data
```

MySQL增加一个**尚不存在**的项目库名：

```sh
node --import tsx scripts/recover.ts /private/full-backup.ccbackup /private/new-chronicle-cartarium-data chronicle_cartarium_recovery_new
```

Windows可把命令里的 `node` 换成安装根 `runtime\node.exe`，路径有空格需引号。目标目录必须全新，已有目标一律拒绝。MySQL私有连接中的服务器必须可访问并有建库权限；迁到另一数据库服务器的配置接入仍需维护者处理，不是网页自动换库。程序不会修改已有原库。

确认恢复成功后采用新目录：直接Node服务设置绝对 `DATA_DIR`；使用启动器的实例先停止服务，再改安装根 `.worldloom/current.json` 的 `dataDir`。该指针优先于环境变量，避免更新后意外回到另一个空目录。检查登录、世界/地图、图片、权限与revision，再允许创作。恢复包里的 `environment.env` 只供维护者私密采用，不自动替换服务器环境。不要删除尚未确认的原数据或失败现场。

## 4. Windows、Linux与macOS，本机与服务器

Windows便携安装使用固定安装根的 `start.cmd`，数据仍在安装目录，程序版本另外存放。普通更新不用手动搬文件或换数据库。固定安装根不能只复制一个新版releases子目录当作整套安装。

Windows桌面版使用相同受管理后端和固定数据目录，后台在线按钮只替换工作台程序；beta.19 起用原生帮助菜单自动升级 Electron 窗口壳；旧壳手动过渡及备用解压方法沿用原工作台目录，不能删除或重新填例。桌面退出或更新中断的边界见[桌面说明](desktop.md)。

Linux 本机使用 `sh start.sh`，macOS 使用 `start.command` 或 `sh start.sh`。对应平台包附带各自架构的 Node/npm 运行时；从源码运行才需另备 Node22.18+ 与 npm。共享启动器用 Node 实现，不依赖盘符；Windows 的 node.exe 不能用于 Linux/macOS。在线入口按平台识别签名更新包；beta.19 为五个发行目标准备更新附件，但不能把它等同于各平台完整升级/失败恢复都已实机验收。旧 Unix 版本首次离线过渡的运行组件要求见[教程](update-guide.md)。各平台的新安装/CI范围见[README支持表](../README.md#版本与平台支持)。

长期服务器的systemd或Windows服务管理器监督固定入口 **`node scripts/launch.mjs`**，工作目录固定为安装根，保留原环境及HTTPS配置。网页只提交受约束更新任务，启动器负责自己的子进程；不能结束其他Node进程，也不执行网页传入的任意命令。直接 `npm start` / `node --import tsx server/index.ts` 属于手动管理，后台会提示使用启动器，完整备份仍可用。

当前启动器继续使用安装根Node运行时启动新版服务，更新包不自动升级此固定运行时；Node大版本升级需单独维护和验收。服务账户需能写安装根`.worldloom`和实际数据目录；只读程序目录应先设计外部可写发布目录，不能假称已支持。

### 从beta.4及更早版本接入beta.5

这是一次手动过渡：所有人保存，停止旧服务，记录**实际**DATA_DIR绝对路径并完整停机备份；将beta.5解压到独立安装根，明确DATA_DIR为原路径并保留私有配置，用新根启动器运行。保留旧程序和数据。若出现安装向导应立刻停下核对路径，不能重新填例。后续beta.5起才可使用受签名更新入口；此beta.5包不能被旧beta.4网页直接导入更新。

没有升级schema，本版保留MySQL 001～005和SQLite1。适配旧安装时不重填范例、不重置账号或更改创作revision。旧程序与数据库之间的兼容要按发行说明确认，不能据此承诺所有未来版本均可直接降级。

## 5. Docker宿主机更新（待实机验收）

容器后台显示宿主机操作指引，不挂Docker socket。宿主机安装Node并在原Compose目录运行一次：

```sh
node scripts/update-docker.mjs trusted-registry/chronicle-cartarium@sha256:完整的64位摘要
```

只有原项目不能由当前目录识别时，前面增加原Compose项目名。必须选择维护者认可的镜像来源和完整摘要；公开镜像为 `ghcr.io/hachimenhato/chronicle-cartarium`，版本及摘要以对应Release为准。镜像标签检查MySQL5/SQLite1，摘要固定内容；**目前没有OCI发布者签名验证**，不能把摘要当身份认证。

现有宿主机脚本固定读取当前目录的 `docker-compose.yml`，不能直接把它当作适配任意Compose文件的一键入口。通过 `docker-compose.image.yml` 或其他自定义文件启动的实例，应先由维护者核对原项目名、配置和实际卷，再采用对应升级流程；不能换目录或重建新项目来规避检查。此限制不影响容器内检查版本，但后台不能自动控制Docker守护进程。

入口查明当前唯一app容器及原持久挂载，先拉取镜像再维护，自动完整备份并复制到宿主机 `.worldloom/host-backups` 校验，再仅替换app。核对实际挂载身份和领域/账号/图片，完成后开放写入。正常Compose更新会重建变化的容器并保留已挂载卷，[官方up说明](https://docs.docker.com/reference/cli/docker/compose/up/)。本入口额外检查实际卷；不能在换目录后默认创建一个空卷。

后续Compose操作继续使用原项目名、原配置以及 `.worldloom/docker-update.json` 覆盖文件。失败时旧镜像从宿主机备份恢复到原卷内新目录/全新项目库，修改DATA_DIR后启动，原数据保留。**不要执行 `down -v`**；它会删除由Compose管理的相关卷，[官方down说明](https://docs.docker.com/reference/cli/docker/compose/down/)。卷配置的身份约束参考[Compose volumes](https://docs.docker.com/reference/compose-file/volumes/)。外部MySQL也在完整备份中，不能仅备份应用卷。

当前Docker新安装、持久卷重启和登录已有amd64 CI，arm64已构建；这不等于宿主机更新与失败恢复全部通过实机验收。主机命令被强行中断后可能保持维护，需要维护者检查状态并完成更新或显式恢复，尚无完整的主机中断续作入口。容器PID命名空间与陈旧实例锁也需进一步演练。

## 6. 发布者与后续开发

发布包白名单不含真实data、`.env`、`mysql.txt`、私有账号、运行控制密钥或开发node_modules。使用 `npm run package:beta` 准备目录，发布者私有签名密钥已配置，运行：

